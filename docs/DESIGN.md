# Technical design and documentation reference

## System flow

Authenticated Hugging Face rows API -> immutable JSON pages + SHA-256 manifest -> Pydantic problem validation -> pandas cleaning and deduplication -> static Python feature extraction -> SQLite -> EDA -> data-quality and exploratory-analysis reports.

Use this as the factual starting point for the daily documentation deliverables. Add actual run counts and interpretations after executing the corresponding day.

## Data dictionary and quality rules

| Field | Type | Meaning / rule |
|---|---|---|
| problem_id | integer | Nonnegative API problem identifier; the unit used for splitting. |
| solutions | JSON-encoded string | API list of Python solution strings; decode before validation of individual solutions. |
| difficulty | string | Source difficulty label; retained for EDA, excluded from model inputs. |
| solution_id | string | Source split, problem ID and solution index. |
| code | string | Nonempty Python source, max 50,000 characters; normalize CRLF and surrounding whitespace. |
| code_hash | string | SHA-256 of cleaned source. |
| canonical_hash | string | SHA-256 of ast.dump with location attributes excluded; catches comment/formatting duplicates. |
| lines | integer | Number of lines in the cleaned source. |
| token_count | integer | Python tokens excluding comments, indentation and newline markers. |
| node_count | integer | Number of nodes visited by ast.walk. |

An API row with truncated cells is rejected. A missing/wrong-type problem field or malformed solutions array is quarantined. An invalid/oversized/unparseable solution is quarantined individually. Python 2 syntax may be rejected by the current Python parser; quantify this limitation. Quarantine entries contain identifiers and reason codes, not source code. Empty solution lists and the five-solution cap are counted separately. Deduplicate globally by AST fingerprint before splitting.

Reconciliation: candidate solutions = accepted unique solutions + duplicates removed + rejected solutions. Whole invalid problem rows are a separate count because their candidate solutions cannot be trusted.

## SQLite schema

`solutions`: solution_id TEXT PRIMARY KEY; problem_id INTEGER NOT NULL; difficulty TEXT NOT NULL; code TEXT NOT NULL; code_hash TEXT NOT NULL; canonical_hash TEXT NOT NULL UNIQUE; lines INTEGER NOT NULL; token_count INTEGER NOT NULL; node_count INTEGER NOT NULL.

`pipeline_runs`: run_id TEXT PRIMARY KEY; summary TEXT NOT NULL (JSON quality summary).

A Day 5 transaction replaces the active canonical solution table and upserts the run summary. It does not delete raw snapshots. This is a single-active-snapshot teaching design, not a multi-tenant production ingestion service.

```sql
SELECT COUNT(*) AS solutions, COUNT(DISTINCT problem_id) AS problems FROM solutions;
SELECT problem_id, COUNT(*) AS n FROM solutions GROUP BY problem_id HAVING COUNT(*) >= 2;
SELECT difficulty, COUNT(*) AS n FROM solutions GROUP BY difficulty;
```

## EDA questions

1. What fraction of candidate solutions is accepted, duplicated or rejected?
2. How many problems have enough distinct solutions for positive pairs?
3. What are the median, tail and outliers of solution length?
4. Which difficulty levels dominate this sample?
5. Are line, token and node counts highly correlated?
6. What selection bias follows from first-row sampling, the solution cap, and syntax filtering?

For each, state the calculation, evidence file, observed result, interpretation, and modeling consequence. Reports generated by Day 6 provide calculations; your written interpretation is a required daily task.

## Stage 1 acceptance and handoff

Run all tests and Day 7. Keep the raw manifest, data dictionary, quality counts, SQLite database, EDA statistics/chart, and interpreted findings together. The gate requires at least 50 problems with two valid distinct solutions so a later modeling stage can construct code pairs. No model training is part of this package.

The API supplies Python solutions grouped by programming problem. This does not provide verified plagiarism labels. Record this limitation in your project scope.
